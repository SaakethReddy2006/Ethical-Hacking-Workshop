Lab 1.3 — Static Analysis Using Detect It Easy (DIE)
🎯 Objective

Use Detect It Easy (DIE) to examine the structure and characteristics of a Windows executable during static malware analysis.

For this demonstration, the benign Windows executable notepad.exe is used as the analysis sample.

🧪 Requirements
Windows analysis VM
notepad.exe
Detect It Easy (DIE)
Isolated malware-analysis environment
⚠️ Safety

This demonstration uses the legitimate Windows notepad.exe executable.

When analyzing actual malware, always use an isolated virtual machine and take a clean snapshot before beginning the analysis.

🖥️ Sample Used
notepad.exe

Default location:

C:\Windows\System32\notepad.exe

Verify that the file exists:

Test-Path C:\Windows\System32\notepad.exe

Expected result:

True
Step 1 — Launch Detect It Easy

Open Detect It Easy (DIE) on the Windows analysis VM.

DIE is a tool used to identify executable formats, architectures, compilers, packers, protectors, and other characteristics of executable files.

Step 2 — Load the Sample

In DIE, open:

C:\Windows\System32\notepad.exe

DIE will automatically analyze the executable.

Step 3 — Examine the File Type

Look at the information displayed by DIE.

Identify the executable format.

For Windows executables, you will generally see information related to:

PE
PE32
PE32+
Windows Executable

Record the format reported by DIE:

File Format: <value shown by DIE>
Step 4 — Identify the Architecture

Examine the architecture information.

Depending on the executable, DIE may identify architectures such as:

x86
x64
ARM
ARM64

Record what DIE reports:

Architecture: <value shown by DIE>

Do not assume the architecture—record the value displayed by your version of DIE.

Step 5 — Examine Compiler Information

DIE may attempt to identify the compiler or linker used to build the executable.

Look for information such as:

Compiler
Linker
Toolchain
Version

Record the result:

Compiler/Linker: <value shown by DIE>

Compiler identification can provide useful information when analyzing unknown executables.

Step 6 — Check for Packers or Protectors

Examine the Packer/Protector information reported by DIE.

A packed executable may be identified with names associated with known packers or protectors.

For example:

UPX
ASPack
Themida
VMProtect

For this demonstration, record exactly what DIE reports:

Packer/Protector: <value shown by DIE>
Important

The presence or absence of a packer is an indicator, not proof of whether a file is malicious.

Step 7 — Examine PE Sections

Inspect the PE section information provided by DIE.

Common PE sections include:

.text
.rdata
.data
.pdata
.reloc

The exact sections depend on the executable and Windows build.

Record the sections displayed by DIE:

.text
<other observed sections>
Why sections matter

PE sections help analysts understand how different types of executable data are organized.

For example:

.text → executable code
.rdata → read-only data
.data → initialized writable data
.reloc → relocation information
Step 8 — Examine the Entry Point

Locate the Entry Point information in DIE.

Record the value shown:

Entry Point: <value shown by DIE>

The entry point indicates where execution begins within the executable.

This information can later be useful when performing deeper reverse engineering in tools such as Ghidra.

Step 9 — Examine Entropy

If your version of DIE displays entropy information, examine the entropy of the executable or its sections.

Record any relevant values:

Entropy: <value shown by DIE>
Understanding Entropy

Entropy measures how random the data appears.

Higher entropy can sometimes indicate:

compressed data
encrypted data
packed executable sections

However, high entropy alone does not prove that an executable is packed or malicious.

It should be correlated with other findings.

Step 10 — Record Your Observations

Create a simple analysis record:

Property	Observation

Only record information actually displayed by your version of DIE.
